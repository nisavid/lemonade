# Backend residency and recovery behavior

## Scope and conclusion

This note answers the backend-research question against upstream Lemonade commit [`a80e5dfae64e7595ed98bd9ee4ad020a43037ea1`](https://github.com/lemonade-sdk/lemonade/commit/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1). The generated upstream support matrix declares ten GPU-capable backend families: `acestep`, `kokoro`, `llamacpp`, `openmoss`, `sd-cpp`, `thenoise`, `thinksound`, `trellis`, `vllm`, and `whispercpp` ([backend matrix](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/docs/dev/backends-reference.md#L10-L73)). `kokoro` is included because Lemonade advertises a Metal variant, although the pinned backend source establishes CPU execution rather than Metal GPU execution; that mismatch is a finding, not a reason to omit the family ([Lemonade descriptor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/kokoro/kokoro.h#L11-L29), [pinned runtime features](https://github.com/lemonade-sdk/Kokoros/blob/d122b52e0ee0a90df26fd041620af36f99e2248a/kokoros/Cargo.toml#L23-L29), [execution-provider selection](https://github.com/lemonade-sdk/Kokoros/blob/d122b52e0ee0a90df26fd041620af36f99e2248a/kokoros/src/onn/ort_base.rs#L6-L28)).

No current combination is `validated` for the accepted residency target because this research performed source inspection, not end-to-end physical tests. Primary evidence is sufficient to model selected operations, but it does not establish a uniform “loaded model” memory shape: some backends retain weights and fixed caches, ACE-Step defers and accumulates component loads after its health check, and ThinkSound and TRELLIS load and free one stage per request ([ACE-Step integration](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/acestep/acestep_server.cpp#L89-L175), [ACE-Step store contract](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/model-store.h#L4-L45), [ThinkSound server](https://github.com/pwilkin/thinksound.cpp/blob/9ee147eaba3b4d2aac75a7ca29d2375d55ff1b70/src/tools/ts-server.cpp#L1-L17), [TRELLIS server](https://github.com/pwilkin/trellis.cpp/blob/d24b02d90b327936f1d08517a35cf2c4e3b1a964/src/trellis-server.cpp#L1-L15)).

Current upstream Lemonade therefore cannot supply predictive memory-capacity admission or verified reclamation by treating every backend process as one model with one byte count. It has count-based admission and a separate reactive global-pressure loop, but neither owns per-domain footprint claims, selects a complete byte-sufficient action set, verifies reclaimed capacity, or recovers descendant ownership after a daemon failure ([count admission](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L230-L302), [pressure selection](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/eviction_engine.cpp#L54-L180), [process handle](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/utils/process_manager.h#L10-L62)). The accepted policy in [ADR 0001](../adr/0001-adopt-protected-memory-capacity-driven-model-residency.md) should remain unchanged; backend and platform adapters must add operation-scoped evidence and mechanisms beneath it.

## Reading the capability recommendations

The recommendations use the accepted vocabulary:

- **Modeled**: immutable primary evidence establishes the affected domain set and enough mechanism or signals to design the operation, but physical validation is still required.
- **Fallback-only**: automation cannot safely rely on a complete footprint or release proof; retain protection and compatibility constraints, make no capacity credit, and surface the limitation.
- **Unsupported**: no safe automatic behavior is established; refuse that automatic operation while leaving explicit manual lifecycle actions distinct.

These are per-operation starting levels, not combination-wide labels. Live signal health can still reduce a modeled operation to its declared fallback or refusal.

## Upstream Lemonade control plane

### Device resolution is not admission-grade

Backend descriptors provide a default device and slot policy, and `WrappedServer` declares `effective_device()` and `effective_slot_policy()` hooks for variant-dependent resolution ([descriptor contract](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/backend_descriptor.h#L47-L80), [effective hooks](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/wrapped_server.h#L440-L460)). No backend overrides either hook at this commit, and the router uses static `model_info.device` plus the recipe descriptor's static slot policy before it constructs and loads the backend ([router admission](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L888-L999)).

The resulting gaps are concrete:

- `llamacpp` defaults to GPU even when its selected variant is CPU or `system`; it changes its live device only inside `load()` ([descriptor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/llamacpp/llamacpp.h#L11-L24), [late update](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/llamacpp/llamacpp_server.cpp#L278-L303)).
- `sd-cpp` defaults to CPU and changes to GPU only inside `load()` for CUDA, Metal, ROCm, or Vulkan ([descriptor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/sdcpp/sdcpp.h#L11-L30), [late update](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/sdcpp/sdcpp_server.cpp#L187-L214)).
- `whispercpp` defaults to CPU, changes Metal and Vulkan to GPU only after admission, and omits ROCm from that GPU branch; its NPU variant likewise reaches NPU classification only after the static Standard slot-policy check ([descriptor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/whispercpp/whispercpp.h#L11-L38), [late update](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/whispercpp/whispercpp_server.cpp#L219-L241)).
- `kokoro` chooses a package named `metal` on macOS but retains its descriptor-default CPU device ([package choice](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/kokoro/kokoro_server.cpp#L31-L40), [load path](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/kokoro/kokoro_server.cpp#L73-L96)).

Resolved intent must consequently include the selected binary variant, custom backend arguments, the backend-native adapter identity or device set, and reconciliation after load. A recipe-level CPU/GPU enum is not sufficient.

### Count and compatibility constraints

All ten families declare `SlotPolicy::Standard`; Standard residents have no accelerator-exclusivity rule and consume the count-managed pool ([slot-policy definition](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/backend_descriptor.h#L23-L29), [family descriptors](https://github.com/lemonade-sdk/lemonade/tree/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends)). Standard pools apply `max_loaded_models` per `ModelType`; routing helpers use one distinct pool per helper model, and `-1` disables the standard count limit ([residency pools](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/model_residency.h#L46-L69), [default count](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/resources/defaults.json#L39-L41)). Pinned residents remain in the count but are excluded from LRU victims; admission fails when a full pool contains no unpinned candidate ([LRU selection](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L253-L302)).

No descriptor expresses multi-adapter occupancy, per-backend internal singleton constraints, transient-operation claims, or a “same physical memory through two API views” alias. Those must become adapter-declared constraints and domain effects rather than new ad hoc eviction precedence.

### Prediction and measurement are separate partial facilities

Lemonade's auto-context path estimates GGUF KV bytes per token and subtracts registry model size from globally available device memory, including VRAM plus GTT for an AMD APU and a unified-memory budget on Metal ([KV estimate](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/auto_tune.h#L27-L63), [available-memory selection](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/auto_tune.h#L84-L193), [context computation](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/auto_tune.h#L195-L220)). The router runs this after count eviction, not as a pre-load multi-resident reservation ([load sequence](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L971-L986)).

The global pressure monitor polls only when global `auto_evict` is enabled and reports a single highest utilization ratio ([monitor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/global_vram_monitor.cpp#L35-L58)). NVIDIA uses `nvidia-smi`; Linux AMD reads VRAM and GTT sysfs counters and, for APUs, takes the stricter of a combined Vulkan view and a preferred-pool ROCm view; Windows uses a DXGI fallback; no Metal pressure source appears in this function ([platform sampler](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/system_info.cpp#L4224-L4341)). These are platform-level aggregate signals, not resident attribution.

The eviction engine scans every loaded server without filtering by device or adapter, skips pins and `IN_USE`, selects one victim by idle time divided by load duration and a configured weight, and does not use bytes reclaimable ([engine](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/eviction_engine.cpp#L54-L180)). GPU pressure can therefore select a CPU/NPU resident, a resident on another adapter, or an idle transient-pipeline process that owns little weight memory. A post-load or post-reclaim aggregate delta can help calibrate a single isolated operation, but cannot by itself prove which resident released which allocation.

### Current soft and hard reclamation semantics

`WrappedServer::downsize()` is a successful no-op by default, yet the eviction engine records a successful call as downsized; only `llamacpp` overrides the method ([default](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/wrapped_server.h#L414-L426), [engine transition](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/eviction_engine.cpp#L150-L173)). The Llama.cpp override erases logical server slots ([wrapper](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/llamacpp/llamacpp_server.cpp#L600-L618)), but the pinned llama.cpp source allocates fixed KV backend buffers at context creation and slot erasure removes sequence ownership without freeing those buffers ([KV allocation](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/src/llama-kv-cache.cpp#L274-L303), [slot erase](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/tools/server/server-context.cpp#L2670-L2692), [sequence removal](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/src/llama-kv-cache.cpp#L366-L416)). It reclaims reusable logical cache content, not demonstrated GPU capacity.

Hard eviction waits for the direct backend to become idle, calls `unload()`, and removes the resident without measuring affected domains afterward ([router eviction](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L593-L627)). A non-file-not-found load failure still takes a separate evict-all-and-retry path, so it does not preserve the accepted planner boundary or pin protection ([retry path](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L1059-L1115), [evict all](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/router.cpp#L629-L648)).

## Backend evidence

### `llamacpp`

- **Placement and allocations.** Lemonade resolves a CPU, CUDA, Metal, ROCm, Vulkan, or Linux system binary, optionally passes an explicit `--device`, and otherwise lets llama.cpp auto-fit and distribute layers ([Lemonade load](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/llamacpp/llamacpp_server.cpp#L278-L395), [llama.cpp device and fit arguments](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/common/arg.cpp#L2638-L2775)). The default layer split is proportional to reported free memory and can affect multiple GPUs; model weights, a fixed KV buffer, compute buffers, optional multimodal projection, and optional draft-model state can therefore span a device set ([layer placement](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/src/llama-model.cpp#L1262-L1335), [KV allocation](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/src/llama-kv-cache.cpp#L274-L303)). Lemonade disables mmap on iGPUs, changing host/GTT behavior relative to the normal mapped-file path ([iGPU argument](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/llamacpp/llamacpp_server.cpp#L389-L395)).
- **Prediction and measurement.** llama.cpp's `--fit` and `--fit-print` are backend-local pre-load facilities, while Lemonade's GGUF auto-context estimator can model weights plus KV at the requested context ([fit arguments](https://github.com/ggml-org/llama.cpp/blob/48d22e295e2b86b47366c16390794f3e05ba970a/common/arg.cpp#L2762-L2788), [Lemonade estimator](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/auto_tune.h#L195-L220)). Neither result is currently converted into an immutable per-domain reservation or reconciled allocation vector.
- **Reclamation.** Slot erasure does not free fixed KV buffers, so current soft reclamation is `unsupported` for memory-capacity credit. Full process exit is available, but verified release and crash recovery are `unsupported` until ownership and per-domain release checks exist.
- **Initial recommendation.** Resolved placement and predictive admission are `modeled` for GGUF configurations whose complete device set and custom arguments can be normalized; unknown tensor overrides, dynamic auto-fit changes, multimodal/draft companions, or stale signals select `fallback-only` with no automatic capacity credit. Measured-pressure attribution remains `fallback-only` pending per-process/per-device measurement.

### `vllm`

- **Placement and allocations.** Lemonade supports ROCm on Linux, passes model and maximum context, enables prefix caching, caps KV at 4 GiB on non-HBM consumer devices unless overridden, and otherwise leaves vLLM's native budgeting in control ([Lemonade launch](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/vllm/vllm_server.cpp#L354-L504)). vLLM binds each worker to its local rank, loads weights into a tagged memory pool, and allocates a shared KV/prefix-cache pool after startup profiling ([device selection](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/vllm/v1/worker/gpu_worker.py#L218-L287), [weight load and KV sizing](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/vllm/v1/worker/gpu_worker.py#L316-L425)). Custom `vllm_args` can expand the affected process and adapter set.
- **Prediction and measurement.** vLLM profiles model weights, activation peaks, non-Torch memory, and free memory before sizing KV; its source explicitly assumes other processes do not change GPU use during profiling and skips CUDA-graph estimation on ROCm ([profile](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/vllm/v1/worker/gpu_worker.py#L331-L425)). This is useful post-spawn reconciliation, not pre-spawn cross-resident admission. vLLM exports KV utilization as a percentage, but Lemonade declares no Prometheus scrape for this backend ([metric](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/vllm/v1/metrics/loggers.py#L519-L526), [descriptor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/vllm/vllm.h#L32-L45)).
- **Reclamation.** vLLM sleep can offload or discard weights and KV on CUDA and ROCm, but online endpoints require both server development mode and `--enable-sleep-mode`; Lemonade enables neither ([sleep guarantees](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/docs/features/sleep_mode.md#L1-L21), [online requirements](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/docs/features/sleep_mode.md#L77-L122), [Lemonade arguments](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/vllm/vllm_server.cpp#L411-L504)). The API server starts a separate EngineCore process, so direct-parent termination is not complete tree proof ([vLLM engine client](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/vllm/v1/engine/async_llm.py#L132-L153)).
- **Initial recommendation.** Post-spawn footprint reconciliation and native sleep are `modeled`; pre-load admission is `fallback-only` until a conservative model/config predictor is calibrated and the complete worker topology is reserved. Hard release and restart recovery remain `unsupported` without process-tree authority and release verification.

### `whispercpp`

- **Placement and allocations.** The pinned server defaults to GPU device index 0 and constructs one persistent context ([server defaults and load](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/examples/server/server.cpp#L90-L110), [context construction](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/examples/server/server.cpp#L649-L715)). The context selects the requested GPU with CPU fallback, allocates persistent model buffers, three fixed KV buffers, and worst-case compute schedulers, and logs their sizes ([device selection](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/src/whisper.cpp#L1290-L1403), [KV allocation](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/src/whisper.cpp#L968-L1017), [state buffers](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/src/whisper.cpp#L3374-L3544)).
- **Prediction and measurement.** The fixed shapes and logged weights/KV/compute sizes make a per-model predictor and post-load parser `modeled`, but Lemonade exposes neither a structured footprint nor the backend-resolved adapter. The current ROCm-as-CPU classification makes even the domain set wrong until fixed.
- **Reclamation.** No backend soft-release endpoint is integrated; KV and scheduler buffers free with the context at reload or process exit ([context reload](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/examples/server/server.cpp#L1127-L1165), [shutdown](https://github.com/ggml-org/whisper.cpp/blob/9386f239401074690479731c1e41683fbbeac557/examples/server/server.cpp#L1242-L1259)). Soft reclamation is `unsupported`; hard release and recovery remain `unsupported` until verified.
- **Initial recommendation.** Placement and admission are `modeled` after variant resolution, ROCm classification, GPU index normalization, and calibration. Otherwise both admission and measured pressure are `fallback-only` with no automatic capacity credit.

### `openmoss`

- **Placement and allocations.** The backend defaults to all GPU layers, selects the GPU with the most free memory, and pins the libllama backbone plus auxiliary embeddings, heads, and optional codec to that one GPU; the codec accounts for approximately 3.4 GiB according to its source contract ([load options](https://github.com/pwilkin/openmoss/blob/64eabe00da0af8374c6fb7f5586e77aa01c2db50/include/openmoss/model.h#L47-L70), [device selection and backbone placement](https://github.com/pwilkin/openmoss/blob/64eabe00da0af8374c6fb7f5586e77aa01c2db50/src/model.cpp#L77-L138), [aux placement](https://github.com/pwilkin/openmoss/blob/64eabe00da0af8374c6fb7f5586e77aa01c2db50/src/model.cpp#L287-L320), [aux allocation](https://github.com/pwilkin/openmoss/blob/64eabe00da0af8374c6fb7f5586e77aa01c2db50/src/model.cpp#L385-L445)). It also owns a libllama KV context and transient codec graphs.
- **Prediction and measurement.** Lemonade passes none of the backend's device, GPU-layer, `skip_codec`, or `aux_cpu` controls and receives no structured footprint ([Lemonade launch](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/openmoss/openmoss_server.cpp#L56-L145)). Model tensors plus context and codec configuration can support a calibrated predictor, but the most-free adapter choice must be reserved and revalidated atomically.
- **Reclamation.** There is no integrated soft release. Full process exit is the only Lemonade reclaim, without release verification.
- **Initial recommendation.** Placement and admission are `modeled` once adapter selection and complete backbone/KV/aux demand are surfaced. Until then, admission and pressure are `fallback-only`; soft reclamation is `unsupported`.

### `acestep`

- **Placement and allocations.** ACE-Step chooses one best GGML GPU backend, shares it across modules, and permits an explicit `GGML_BACKEND` override ([backend selection](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/backend.h#L62-L115)). Its component store owns language-model, encoder, DiT, VAE, and tokenizer modules; the language-model key includes maximum sequence and KV-set count ([store types](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/model-store.h#L61-L88)). The default store keeps at most one GPU module, but `--keep-loaded` accumulates them; Lemonade always passes `--keep-loaded` ([store policy](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/model-store.h#L4-L28), [Lemonade arguments](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/acestep/acestep_server.cpp#L117-L124)).
- **Prediction and measurement.** The store records weight-buffer bytes and exposes an internal total used by backend tests, but that excludes other allocations and is not exported to Lemonade ([store observability](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/model-store.h#L130-L134), [weight accounting](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/model-store.cpp#L240-L290)). Load readiness precedes the workload-dependent component allocations, so process load duration and a post-start delta do not describe steady demand.
- **Reclamation.** The backend already has component eviction, but Lemonade selects the never-evict mode and has no adapter operation for it. Hard process exit frees every store entry ([store shutdown](https://github.com/pwilkin/acestep.cpp/blob/ff717c94c4ee0011b88cf305355a622db2c0a12d/src/model-store.cpp#L162-L195)).
- **Initial recommendation.** Adapter identity and component-level soft reclamation are `modeled`; startup admission is `fallback-only` until workload intent yields a conservative component/KV working-set vector. Do not credit a healthy idle process with zero demand or score it by startup time. Hard release and recovery remain `unsupported` until verified.

### `sd-cpp`

- **Placement and allocations.** stable-diffusion.cpp has per-module runtime and parameter backends, supports stream-layers, eager loading, and a maximum-VRAM assignment, and records parameter memory by model group ([backend state](https://github.com/leejet/stable-diffusion.cpp/blob/8caa3f908ae6d4a4bef531e73b9a969f266a3d1f/src/stable-diffusion.cpp#L172-L290), [configuration](https://github.com/leejet/stable-diffusion.cpp/blob/8caa3f908ae6d4a4bef531e73b9a969f266a3d1f/src/stable-diffusion.cpp#L344-L395), [parameter accounting](https://github.com/leejet/stable-diffusion.cpp/blob/8caa3f908ae6d4a4bef531e73b9a969f266a3d1f/src/stable-diffusion.cpp#L598-L638)). Its persistent context can retain text encoder, diffusion, VAE, control, extension, and LoRA weights; inference adds graph/workspace and latent allocations rather than an LLM KV cache ([context members](https://github.com/leejet/stable-diffusion.cpp/blob/8caa3f908ae6d4a4bef531e73b9a969f266a3d1f/src/stable-diffusion.cpp#L172-L218), [server runtime](https://github.com/leejet/stable-diffusion.cpp/blob/8caa3f908ae6d4a4bef531e73b9a969f266a3d1f/examples/server/runtime.h#L48-L59)).
- **Prediction and measurement.** Lemonade selects a binary variant and permits custom `sdcpp_args`, but it does not resolve module-to-domain placement or ingest the backend's parameter and graph limits ([Lemonade arguments](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/sdcpp/sdcpp_server.cpp#L187-L291)). A normalized backend configuration plus parameter metadata can model persistent demand; resolution, workload dimensions, and graph peaks are required for transient demand.
- **Reclamation.** Streaming or CPU/disk parameter placement is a load configuration, not a current Lemonade soft operation. Destroying the stable-diffusion context releases the backend object, but Lemonade verifies only direct process termination ([context destruction](https://github.com/leejet/stable-diffusion.cpp/blob/8caa3f908ae6d4a4bef531e73b9a969f266a3d1f/src/stable-diffusion.cpp#L3040-L3066), [Lemonade unload](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/sdcpp/sdcpp_server.cpp#L393-L401)).
- **Initial recommendation.** Placement and persistent-footprint admission are `modeled` only for normalized module-backend configurations; transient operation admission is `fallback-only` until graph/workspace peaks are calibrated per request shape. Soft reclamation is `unsupported` unless a backend operation is added and verified.

### `thenoise`

- **Placement and allocations.** TheNoise runs one ROCm model on Torch's `cuda` device alias, holds one model at a time, and swaps by deleting it, collecting garbage, and emptying the Torch cache ([runtime](https://github.com/lemonade-sdk/thenoise/blob/2b931caf6685f815788791a391bb94a246b2eb49/thenoise/runtime.py#L1-L78)). The persistent model includes DiT, VAE, text encoder, active LoRA state, optional upscaler, and a single-entry on-device prompt/sampling/decode cache ([model cache contract](https://github.com/lemonade-sdk/thenoise/blob/2b931caf6685f815788791a391bb94a246b2eb49/thenoise/models/base.py#L38-L60), [persistent state](https://github.com/lemonade-sdk/thenoise/blob/2b931caf6685f815788791a391bb94a246b2eb49/thenoise/models/base.py#L139-L182), [cache release](https://github.com/lemonade-sdk/thenoise/blob/2b931caf6685f815788791a391bb94a246b2eb49/thenoise/utils/pipeline_cache.py#L1-L15)).
- **Prediction and measurement.** Lemonade supplies paths and launches the backend but receives no resolved adapter, Torch allocation breakdown, or cache footprint ([Lemonade launch](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/thenoise/thenoise_server.cpp#L68-L159)). Model tensor metadata can seed a predictor, but compile/runtime allocator reserves and workload-shaped result caches require calibrated post-load and post-operation signals.
- **Reclamation.** The backend has a cache-clear primitive and model-unload cleanup internally, but Lemonade exposes neither as a downsize endpoint; `torch.cuda.empty_cache()` does not release live tensors ([cache clear](https://github.com/lemonade-sdk/thenoise/blob/2b931caf6685f815788791a391bb94a246b2eb49/thenoise/utils/pipeline_cache.py#L119-L125), [runtime unload](https://github.com/lemonade-sdk/thenoise/blob/2b931caf6685f815788791a391bb94a246b2eb49/thenoise/runtime.py#L66-L78)).
- **Initial recommendation.** Persistent-weight admission and internal result-cache reclamation are `modeled` after adding structured adapter/tensor/cache reporting and an idle-only clear endpoint. Until then, admission and pressure are `fallback-only`; hard release and recovery remain `unsupported` until verified.

### `thinksound`

- **Placement and allocations.** ThinkSound picks the GPU with the greatest total memory unless overridden, then serially loads and destroys T5, CLIP, DiT, and VAE stages for every request ([device selection](https://github.com/pwilkin/thinksound.cpp/blob/9ee147eaba3b4d2aac75a7ca29d2375d55ff1b70/src/common/ts_backend.h#L7-L35), [stage lifecycle](https://github.com/pwilkin/thinksound.cpp/blob/9ee147eaba3b4d2aac75a7ca29d2375d55ff1b70/src/tools/ts-server.cpp#L46-L100)). The idle server retains tokenizers and process/backend runtime, not model-weight GPU residency; the operation peak is approximately one stage plus its tensors and workspace.
- **Prediction and measurement.** Lemonade records the process as a loaded GPU model but neither resolves the backend-selected adapter nor predicts request-stage peaks ([Lemonade launch](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/thinksound/thinksound_server.cpp#L59-L153)). Hard-evicting an idle process can therefore recover little GPU capacity.
- **Reclamation.** Per-stage destruction already performs the meaningful weight reclaim after each operation. There is no additional idle soft state to clear through Lemonade.
- **Initial recommendation.** Idle residency admission is `modeled` as a small runtime claim only after measurement; request admission is `fallback-only` until every stage peak is bounded for the requested duration/shape. Operation-completion reclamation is `modeled`; pressure-driven idle hard eviction must receive no unverified weight-recovery credit.

### `trellis`

- **Placement and allocations.** TRELLIS selects the requested CUDA device or the generic GPU with greatest total memory, but falls back to CPU unless `--require-gpu` is set; Lemonade does not reserve that flag ([backend selection](https://github.com/pwilkin/trellis.cpp/blob/d24b02d90b327936f1d08517a35cf2c4e3b1a964/src/trellis_model.cpp#L31-L75), [Lemonade arguments](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/trellis/trellis_server.cpp#L62-L113)). Each request loads and frees a sequence of model stages; the resident process primarily avoids Vulkan reinitialization ([server contract](https://github.com/pwilkin/trellis.cpp/blob/d24b02d90b327936f1d08517a35cf2c4e3b1a964/src/trellis-server.cpp#L1-L15), [weight-buffer allocation and free](https://github.com/pwilkin/trellis.cpp/blob/d24b02d90b327936f1d08517a35cf2c4e3b1a964/src/trellis_model.cpp#L77-L150)).
- **Prediction and measurement.** The model exposes tensor bytes internally, but Lemonade has no stage plan, backend-resolved adapter, or transient measurement ([tensor total](https://github.com/pwilkin/trellis.cpp/blob/d24b02d90b327936f1d08517a35cf2c4e3b1a964/src/trellis_model.cpp#L138-L150)). A declared GPU variant can silently run on CPU, invalidating the domain claim.
- **Reclamation.** Per-stage destruction is the meaningful reclaim; idle downsize is a no-op and idle process eviction may recover little GPU memory.
- **Initial recommendation.** Require and reconcile GPU placement before any GPU-capacity cell can be `modeled`. Idle residency is otherwise `fallback-only`; request admission is `fallback-only` until complete stage peaks are bounded; operation-completion reclamation is `modeled` after physical validation.

### `kokoro`

- **Placement and allocations.** Lemonade chooses an archive named `metal` on macOS and advertises Metal support ([package selection](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/kokoro/kokoro_server.cpp#L31-L58), [descriptor](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/backends/kokoro/kokoro.h#L11-L29)). The pinned Rust source defines only CPU and CUDA features and explicitly selects the CPU ONNX execution provider when CUDA is absent; it contains no Metal/CoreML execution-provider path ([features](https://github.com/lemonade-sdk/Kokoros/blob/d122b52e0ee0a90df26fd041620af36f99e2248a/kokoros/Cargo.toml#L23-L29), [provider selection](https://github.com/lemonade-sdk/Kokoros/blob/d122b52e0ee0a90df26fd041620af36f99e2248a/kokoros/src/onn/ort_base.rs#L6-L28)).
- **Prediction, measurement, and reclamation.** Primary source therefore establishes host/CPU residency for the pinned macOS artifact design, not GPU weights or GPU cache behavior. Lemonade has no GPU footprint or soft-reclaim integration and stops only the direct process ([unload](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/backends/kokoro/kokoro_server.cpp#L150-L157)).
- **Initial recommendation.** Every GPU residency operation is `unsupported` until an actual GPU execution path is proven and the Lemonade support declaration is corrected or implemented. Keep Kokoro out of GPU capacity and pressure candidate sets meanwhile.

## Process-tree ownership and recovery

Every backend wrapper ultimately stores only a native handle and PID; there is no daemon epoch, launch nonce, non-reusable process-start identity, descendant scope, or durable ownership record ([process handle](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/include/lemon/utils/process_manager.h#L10-L62)). Backend readiness proves that an HTTP endpoint responds, not that the expected device set and memory claim match the admission intent.

Platform facilities are uneven:

- Linux uses `fork`/`exec` and sets `PR_SET_PDEATHSIG(SIGTERM)` on the direct child, but unload signals only that PID, waits, escalates, and sleeps a fixed two seconds; it neither owns a process group nor verifies descendants or device-memory release ([spawn](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/utils/platform/process_linux.cpp#L138-L205), [termination](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/utils/platform/process_linux.cpp#L307-L364)).
- macOS uses `posix_spawn` without a containment scope and terminates only the direct PID, followed by the same fixed delay ([spawn](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/utils/platform/process_macos.cpp#L84-L210), [termination](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/utils/platform/process_macos.cpp#L274-L331)).
- `ProcessManager` on Windows uses `CreateProcess` and terminates only the tracked handle ([spawn and termination](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/server/utils/platform/process_windows.cpp#L288-L361)). The embedded Windows tray executable separately creates a kill-on-close Job Object and assigns itself so descendants inherit containment, but standalone `lemond` does not establish that authority in `ProcessManager` ([tray containment](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/tray/main.cpp#L37-L60), [tray initialization](https://github.com/lemonade-sdk/lemonade/blob/a80e5dfae64e7595ed98bd9ee4ad020a43037ea1/src/cpp/tray/main.cpp#L124-L133)).

The risk is highest for backends that create descendants. vLLM always starts an EngineCore background process behind its API process ([engine creation](https://github.com/vllm-project/vllm/blob/132765e3560659ff63ebd236203672e991b70e08/vllm/v1/engine/async_llm.py#L132-L153)); other Python or launcher-based backends must be treated as potentially multi-process until their exact launch tree is captured and validated. A PID-only record cannot safely distinguish a restarted process from PID reuse or prove ownership of an orphan.

The platform/recovery starting profile is therefore:

| Operation | Windows embedded tray | Windows standalone `lemond` | Linux | macOS |
|---|---|---|---|---|
| Normal direct-child stop | Modeled by handle and wait, but release is unverified | Modeled by handle and wait, but release is unverified | Modeled by owned-child wait, but release is unverified | Modeled by owned-child wait, but release is unverified |
| Complete descendant containment | Modeled by kill-on-close Job Object; requires crash-injection validation | Unsupported | Unsupported: parent-death signal covers only the direct child | Unsupported |
| Durable restart ownership and cleanup | Unsupported | Unsupported | Unsupported | Unsupported |
| Per-domain resource-release proof | Unsupported | Unsupported | Unsupported | Unsupported |

No planner may credit hard-reclaimed memory or release count/compatibility claims merely because `unload()` returned. Until a platform/backend cell has validated containment or a crash-consistent ownership record plus release checks, an ambiguous outcome must retain quarantine claims as required by ADR 0001.

## Operation capability and fallback matrix

These are recommended initial implementation cells from the evidence above. `M` means modeled, `F` fallback-only, and `U` unsupported. No cell is validated.

| Backend | Resolve affected GPU domain set | Predict admission footprint | Reconcile post-load footprint | Automatic measured-pressure action | Soft memory reclamation | Verified hard release/recovery |
|---|---:|---:|---:|---:|---:|---:|
| `llamacpp` | M after normalized device/split resolution | M for normalized GGUF/context; F otherwise | F until per-device attribution exists | F: report pressure, do not credit unattributed eviction | U: slot erase retains fixed KV buffers | U |
| `vllm` | M after full worker topology resolution | F before spawn | M from backend profile after reservation | F until worker/device attribution and release checks exist | M through native sleep after safe integration | U |
| `whispercpp` | M after variant and GPU-index fixes | M from fixed model/KV/compute shapes | M from structured log/API adaptation | F until attribution and release checks exist | U | U |
| `openmoss` | M after reserving most-free adapter choice | M after backbone/KV/aux calibration | F until structured attribution exists | F | U | U |
| `acestep` | M after backend identity is surfaced | F: workload-dependent deferred component set | F; internal weight counter is incomplete and unexported | F | M through component-store policy after integration | U |
| `sd-cpp` | M for normalized per-module backends | M for persistent parameters; F for transient graph peaks | F until structured per-domain reporting exists | F | U for dynamic reclaim; load-time streaming is distinct | U |
| `thenoise` | M after Torch adapter identity is surfaced | M for persistent tensors; F for compile/cache/transient peaks | F until Torch allocation reporting exists | F | M for result-cache clear after endpoint and verification | U |
| `thinksound` | M after backend identity is surfaced | F for per-request transient stage peaks | F until stage measurement exists | F: idle hard eviction gets no weight credit | M for operation-completion stage release | U |
| `trellis` | F until GPU-only placement is required and reconciled | F for per-request transient stage peaks | F until stage measurement exists | F: idle hard eviction gets no weight credit | M for operation-completion stage release | U |
| `kokoro` | U: pinned source is CPU-only | U | U | U: exclude from GPU candidates | U | U for GPU residency |

The fallback implied by every `F` cell is conservative and operation-specific: preserve pins and in-use protection; retain every plausible memory, count, compatibility, and adapter claim; do not automate a capacity-dependent incoming load; do not count an unverified action toward a deficit; and expose the missing signal or adapter capability. A manual unload or explicit force remains a separate lifecycle action and does not upgrade the automatic cell.

## Implementation implications

The common planner should require backend adapters to report, per resolved intent and operation:

1. the exact adapter and memory-domain set, including aliases such as Hatchery's GTT-backed model allocations;
2. persistent weights, fixed KV or prefix pools, reconstructible result caches, transient workspaces, allocator reserves, and host-memory effects as distinct vector components;
3. lifecycle phase (`startup`, `idle`, `active`, `first-use`, or named pipeline stage) and a predicted range with confidence;
4. the backend-native operation, eligibility, expected domain effects, and verification signal for every reclaim level;
5. the complete process-tree or containment identity and the recovery authority established before spawn; and
6. backend-internal count, singleton, and compatibility constraints in addition to Lemonade's Standard count pool.

The first implementation slice should not pretend that all cells are portable. Hatchery can validate the GTT domain for selected ROCm backends first, but adapter APIs and stored capability profiles must preserve the distinctions above so later platform tickets can advance cells without redefining common policy.
