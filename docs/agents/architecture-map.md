# Architecture Map

This file captures implementation landmarks that are useful before changing Lemonade, but too implementation-specific for `CONTEXT.md`. Sections describe the checked-out fork unless they are explicitly labelled as an accepted target.

## Process Topology

- `lemond` is the pure HTTP server process.
- `lemonade` is the CLI client.
- `LemonadeServer.exe` embeds `lemond` on Windows and provides the always-on tray icon.
- `lemonade-tray` is the macOS/Linux tray client.
- `lemonade-server` is a deprecated compatibility shim.
- Backends run as subprocesses; do not move inference engines in-process without an explicit architecture decision.

## Server Core

- `src/cpp/server/server.cpp` registers HTTP routes, serves the web app, applies auth, and owns endpoint handlers.
- Core API endpoints are registered under `/api/v0/`, `/api/v1/`, `/v0/`, and `/v1/`.
- Ollama-compatible routes live under `/api/` without the Lemonade/OpenAI version prefix.
- Internal endpoints live under `/internal/`: `shutdown`, `set`, `config`, and `cleanup-cache`. They are loopback-restricted admin/local lifecycle, configuration, and cache-management APIs, not OpenAI-compatible routes.
- The checked-out fork exposes configured pin management as `GET /pins`, `POST /pins`, and `DELETE /pins/{model_name}` under `/api/v0/`, `/api/v1/`, `/v0/`, and `/v1/`.

## Model Lifecycle

- `Router` (`src/cpp/server/router.cpp`) selects loaded servers, applies model-type LRU, enforces NPU constraints, and forwards inference.
- `WrappedServer` (`src/cpp/include/lemon/wrapped_server.h`) is the in-process abstraction for one backend subprocess.
- `ModelManager` (`src/cpp/server/model_manager.cpp`) loads built-in and user registries, resolves paths, registers user models, discovers extra GGUF models, and downloads artifacts.
- `server_models.json` is the built-in model registry.
- `backend_versions.json` pins downloadable backend artifact versions.
- `recipe_options.json` stores per-model runtime options in the Lemonade cache.

## Current Cache and Eviction

- Model type controls the LRU bucket: LLM, embedding, reranking, audio, image, or TTS.
- `max_loaded_models` applies per model type, not globally.
- `max_gpu_memory_occupancy_gb` applies across loaded GPU models. Router dry-runs largest-to-smallest GPU evictions and leaves existing models loaded when the requested model cannot fit.
- Configured pins live in `pinned_models`, are loaded at startup, do not consume count-managed slots, and are excluded from ordinary automatic capacity victims.
- An incoming pinned NPU/FLM model can evict an incompatible pinned incumbent. This last-pinned-load-wins behavior is unsafe and is replaced by the accepted target below.
- Busy `WrappedServer` instances are protected from eviction until their active request ends.
- The load-failure retry path preserves configured pins but can evict every eligible unpinned model before retrying.
- This ref has no upstream-style reactive pressure engine or idle KV-cache reclamation.

## Accepted Model Residency Target

- This accepted fork target is recorded in `docs/adr/0001-adopt-protected-memory-capacity-driven-model-residency.md`.
- The accepted portable adapter, footprint, pressure-reclamation, configuration, explanation, validation, and promotion policies and their decision rationale live in [Choose portable residency adapter contracts](https://github.com/nisavid/lemonade/issues/31), [Choose footprint estimation and confidence policy](https://github.com/nisavid/lemonade/issues/32), [Choose portable pressure reclamation controls](https://github.com/nisavid/lemonade/issues/33), [Define portable residency configuration and explanations](https://github.com/nisavid/lemonade/issues/34), and [Define residency validation and capability promotion](https://github.com/nisavid/lemonade/issues/35); the bullets below are their scout map.
- Continued fork maintenance is decided. Reconcile onto current stable upstream, then implement this target using upstream terminology and APIs where they fit.
- One server-owned planner defines admission, pressure, protection, ordering, and refusal semantics. Platform and backend adapters describe residency-memory-domain topology, trustworthy capacity and pressure signals, footprint confidence, and available reclamation actions; adapters do not redefine common policy.
- The portable contract has three authority domains. Platform providers report hardware/OS topology, observations, health, and containment primitives. Backend adapters report backend/device resolution, lifecycle-shaped predicted and observed effects, raw mechanism availability, and launch requirements. The server-owned control plane validates every envelope, issues canonical identities, compiles actions, owns the capability catalog, lifecycle mutation gate, constraint ledger, planner, and recovery subsystem, and makes every policy decision.
- Every adapter family uses a centrally validated versioned envelope. Unknown majors, required features, kinds, provenance, or affected scopes fail closed; unknown data never becomes zero capacity, an empty claim set, a successful no-op action, or a healthy default.
- The composite topology resolver keeps physical backing resources, residency memory domains, provider measurement views, and operational constraint instances distinct. It alone canonicalizes aliases and correlation evidence. A topology change fences new effects, drains or reconciles old generation tokens, retains old claims, and atomically rebinds exact identities; ambiguous mappings become shared-unknown quarantine rather than independent capacity.
- Predicted and observed resource effects use server-issued typed identities and explicit logical-to-observed allocation-group reconciliation. Effects distinguish persistent weights, fixed cache, reconstructible state, transient workspace, allocator reserve, and host effects. Every effect carries its complete atomic claim set; splitting, coalescing, and shared allocations must be proven without double counting.
- Footprint entries form one portion of the server-built completeness manifest; footprint confidence never substitutes for complete capacity, safety-floor, cardinality, compatibility, action-lease, and ownership/recovery claims. Each bounded component has a reviewed derivation, conservative upper bound, uncertainty and provenance, one logical allocation group for its physical bytes and alias-linked memory/host effects, and cataloged liveness in a closed lifecycle model. Cardinality and compatibility claims attach once at their resident or operation scope rather than repeating per allocation group.
- Predict weights, fixed cache, reconstructible state, transient workspace, allocator reserve, and host effects analytically wherever reviewed model, encoding, placement, cache, request-shape, and backend rules permit. Maximize each constraint over reachable simultaneously-live component sets, including retained state and concurrent requests; do not sum mutually exclusive stages or assume overlap is transitive. Use a cataloged residual envelope only for recognized allocator/runtime uncertainty. A missing component is not residual, and an unmodeled reachable set makes the manifest incomplete.
- A reviewed capability catalog derives footprint confidence, required observations and freshness, recovery and discovery mechanisms, reclamation protocols, accepted capability, fallback, and refusal from attested runtime evidence. The compact compiled catalog ships with the consuming fork release; larger sanitized evidence is a separate content-addressed release asset with an independently administered backup. Runtime observations remain local and report-only initially. The catalog, discovery profiles, mechanism contracts, and applied evidence are immutable content-addressed recovery objects. Journal references bind their exact versions and cannot be reinterpreted more permissively after reload or restart.
- Evidence liveness uses an independently administered append-only witness for compact catalog and evidence-manifest sequence, digest, identity, signature, and lease metadata. The witness is not bulk profile storage, observation collection, fitting, curation, or redistribution. Missing, stale, rolled-back, or unverifiable authority caps dependent promotion units at their cataloged concrete fallback until fresh authority is established.
- Footprint confidence has five closed classes. `enforced_complete` externally prevents effects from exceeding a complete envelope. `validated_predictor` has reviewed component bounds and representative physical validation of applicability, coverage, and residual for the full catalog cell. `calibrated_instance` is a reviewed exact-fingerprint bound restricted to an explicitly requested, isolated validation or discovery operation. `incomplete` and `unknown` cannot authorize startup or ordinary admission. Startup and ordinary capacity-dependent load require `validated_predictor` or `enforced_complete`, subject to stricter catalog policy; a matching validated predictor instantiates for a new model without per-model calibration.
- Calibration validates component coverage and bounds only the recognized residual. Bind every sample to the content-addressed catalog cell and all material model, tensor/cache, request-shape, platform, backend, runtime, driver, configuration, topology, placement, recovery, and workload identities. Aggregate samples require stable before/during/after observations and rejection when unattributed demand changes beyond uncertainty. Runtime evidence never mutates an active bound or promotes confidence; an exceedance invalidates the fingerprint, fences work and growth, and quarantines the violating resident until verified release. Only a reviewed catalog revision can change derivations, residuals, applicability, compatibility, exact-instance calibration, or confidence.
- One lifecycle mutation gate composes owner-lease fencing and the topology, catalog, discovery, configuration, observation, daemon, and journal generations. Ordinary lifecycle work requires a fully ready token. A scoped recovery-remediation token may only strengthen quarantine, rebind evidence, perform authorized cleanup, verify release, and catch up the ledger; it cannot route, admit, grow, weaken claims, or bypass verified-release rules.
- The common claim algebra has four closed kinds: consumable capacity, safety floor, cardinality pool, and compatibility/exclusivity. A server-built completeness manifest covers every applicable claim before the first side effect. Initial runtime realization may only narrow the pre-spawn envelope; later growth requires a separately cataloged, externally gated transaction that reserves and journals a conservative superset before the effect.
- The durable recovery/claim journal is the only persisted claim authority; the runtime ledger is solely its ordered projection. Live processes and allocations are reconciliation evidence, never a second authority or automatically adopted residency. Bootstrap proves complete coverage only for independently marked or plausibly Lemonade-owned resources; unrelated applications remain external capacity/pressure observations.
- Every resource-owning launch prepares a journal record before spawn and uses either hereditary containment or externally mediated durable membership. Prepared nonce, maximum complete claims, catalog/evidence identities, and intended scope bind atomically to process creation before resource ownership. Envelope violations invalidate the bound, fence the resident, and quarantine the complete plausible claim set.
- Restart recovery is cleanup-only. Every non-released prior-epoch record becomes non-routable quarantine. After the prior owner is proven dead or fully effect-fenced, `owner_scoped_cleanup` ignores stale prior-epoch pin/in-use metadata, uses the last proven recovery authority, and retains every claim until complete release is verified. Ambiguous ownership is never signaled.
- The journal validates a closed launch-phase/disposition transition table. Known-owned and fully bounded policy invalidation enters `suspended` immediately; only same-epoch full re-attestation may restore it to active. Any ambiguity enters `quarantined`, which can exit only to verified `released`.
- A finite pre-spawn candidate set compiles to the union of all candidate claims, maxima, prerequisites, and observation dependencies under the most conservative thresholds and least-permissive disposition. Every candidate must authorize the discovery spawn under one recovery authority. Post-spawn realization must match exactly one cell and may narrow but never enlarge the prepared permission or reservation.
- The normalized [portable support inventory](../research/portable-residency-capability-inventory.json) and its human-facing [capability matrix](../research/portable-residency-capability-matrix.md), bound to an immutable upstream support baseline and checked by `tools/validate_residency_capability_inventory.py`, cover every upstream-supported GPU platform and backend family conceptually. Atomic backend variants reference finite platform, operation, constraint, recovery, fallback, and suite IDs; exact runtime cells add material topology, configuration, and evidence identities. The evidence-only NPU/FLM compatibility contract has a separate identity over its frozen source baseline, exact source-derived cases, relation coverage, `NPC` selector, enumerated relation constraints, evidence/gate sets, state, and fallback. It proves only those relation constraints. Participant-local slot cardinality, ownership, protection, claim replay, cleanup, and recovery require separate exact promotion units; the relation contract grants no runtime authority, and `delivery_state=absent` keeps it unavailable even when synthetic evidence exists. Physical qualification creates exact platform cells. GPU residency is in scope, current NPU coexistence remains in this route, and CPU residency is excluded. A combination-wide label is a derived display summary, never a policy input.
- Every promotion unit keeps four state dimensions distinct: `evidence_ceiling` is the strongest capability its frozen evidence program could justify; `capability_level` is the level actually accepted by the reviewed catalog; `delivery_state` is `absent|implemented_unverified|release_verified` for the complete runtime-cell or compatibility-contract unit; and live signal, evidence-liveness, and recovery health are runtime facts. Accepted design or a planned ceiling never changes the other dimensions.
- Effective residency mode is the conservative meet of configured intent, delivery state, accepted capability level, evidence-liveness authority, required live signals, and recovery readiness. Plans snapshot every relevant generation and revalidate it at plan creation, plan or action reservation, each capacity-affecting dispatch, incoming-load commit, and terminal claim transfer. Missing, stale, or unhealthy authority selects the declared concrete fallback or refusal, and any post-reclamation change stops the remaining plan under the partial-outcome policy.
- Each operation's cataloged admission baseline declares whether an observation is device-wide capacity/use, an external-pressure-sensitive allowance or budget, process/application usage, or a backend heap; its allocation-group and owner coverage; and its topology, generation, freshness, uncertainty, and health. The control plane composes observations with claims only when coverage proves what is included, excluded, or aliased. External application demand consumes the available allowance without becoming a Lemonade claim. Possibly Lemonade-owned unattributed demand enters quarantine under the smallest provable shared-unknown lifecycle scope, with the union of plausible ordinary, action-lease, and ownership/recovery claims retained.
- Pins consume `max_loaded_models` slots and are never automatic LRU victims. Hatchery disables the count ceiling with `max_loaded_models=-1` and uses the capacity policy as its primary admission bound.
- `recipe_options.json` is the source of durable per-model pin preference. A global `load_pinned_models_on_startup` policy, defaulting to false, controls whether `lemond` attempts grouped startup admission of those models.
- Startup failures are logged and surfaced without preventing `lemond` from starting. A saved pin preference remains visible even when its model is not resident.
- Startup loading first resolves every saved preference into an immutable admission intent containing model identity, recipe, backend and device, saved options, topology, count category, effective mode, configuration and signal generations, and predicted constraint effects. It builds connected startup admission sets from those intents, revalidates their identities when reserving a set, and waits or invalidates before mutation if relevant configuration changes.
- Preferences belong to the same startup admission set when their resolved intents share any capacity, host-health, count, compatibility, or adapter-declared constraint. An independent set proceeds only when the planner can jointly admit every member under its current effective modes; an infeasible set loads none, preserves every saved preference, and surfaces a conflict for every member. Registry, JSON, container, and execution order never grant precedence.
- The plan coordinator reserves a complete feasible startup admission set before its first load. Members materialize in deterministic order as owner-scoped, non-routable provisional loads without runtime pins. Each load is reconciled against its intent and reservation before the next begins. Once every member is verified, one atomic commit publishes the complete set as routable residents, converts claims to committed occupancy, and applies runtime pins.
- Any pre-commit load failure, signal or configuration change, cancellation, reconciliation mismatch, or reservation invalidation aborts the set and rolls back every provisional member. Cleanup is transaction-owned rather than automatic reclamation of a committed pin. Reconcile and report partial or quarantined outcomes when rollback cannot restore the pre-attempt state. Other independent feasible sets may still load, and `lemond` still starts.
- Saved preferences are the only durable desired startup state, not the only durable operational recovery state. Before starting lifecycle subsystems, `lemond` acquires an exclusive daemon/recovery-store owner lease for its cache and constraint ledger. A second daemon cannot classify a live owner's children as orphans; while another owner is live or ownership is uncertain, model lifecycle remains not ready and refuses mutation explicitly.
- Before any backend spawn, its platform/backend path durably prepares one recovery-authority record and selects exactly one cataloged mode: hereditary containment or externally mediated durable membership. The record contains the daemon epoch, unique launch nonce, resolved intent, maximum complete constraint claims, applied catalog/evidence identities, and intended containment/tree scope. Process creation atomically binds the nonce or containment identity to the child tree; before the plan advances, the record transitions monotonically to a non-reusable process-start identity and complete descendant scope. PID alone is never ownership proof.
- Every daemon crosses one recovery barrier before starting the startup-pin loader, pressure engine, or any other automatic residency work and before a model-lifecycle endpoint may mutate state. The barrier replays every ownership record into the constraint ledger as maximum-claim quarantine, proves the prior owner dead or fully effect-fenced, and releases claims only after matching the full launch/process identity and verifying complete tree and resource release. It never adopts prior-epoch survivors. Incomplete, malformed, reused-PID, live-owner, or otherwise ambiguous records retain quarantine claims or block the affected lifecycle scope; they block all lifecycle when that scope cannot be proven. Cleanup never signals a process whose ownership is uncertain. Non-lifecycle health may expose recovery progress, while lifecycle requests receive an explicit unavailable or retry response.
- If a platform/backend cannot provide either recovery-authority mode with trustworthy identity, complete ownership coverage, and verified release, its affected operation must select its cataloged concrete fallback or refuse.
- Hatchery is the first behavioral reference profile and initial validation target, not an implementation freeze or an already validated combination. The accepted [validation profile](../research/hatchery-residency-validation-profile.md), [campaign parameters](../research/hatchery-campaign-parameters.md), and [profile-free estimator design](../research/profile-free-residency-estimation.md) qualify `llamacpp:rocm` first; Vulkan is a separate later cell and cannot borrow ROCm evidence. Hatchery's residency memory domain is GTT/shared GPU memory, which accounts for resident model weights and caches; host `MemAvailable` is an independent system-health interlock and is never added to GTT usage.
- On shared-memory systems, admission requires both predicted residency-domain headroom and the post-admission host-memory safety floor. Breaching either is a pressure trigger. The planner evaluates one constraint vector containing every deficient residency domain and the separate host-floor deficit; each action maps a unique physical allocation to its effects on those constraints, so reclaiming shared bytes may improve both without counting them as two allocations.
- The server binds one immutable pressure-policy profile to each canonical constraint identity during catalog and topology composition. Aliased capability cells reuse it; disagreement fails closed. A quantitative controller normalizes its signal to a signed safety margin; a qualitative or rate controller uses cataloged ordered semantics and a complete conservative recovery target and effect model. Every controller owns `normal`, `reclaim`, `critical`, and `recovery_pending` phases; distinct reclaim-entry, critical-entry, and recovery-exit predicates; hard-action dwell and recovery stabilization durations; monotonic timestamps; and invariant generation bindings. `critical` waives only the remaining hard-reclamation dwell, never freshness, complete planning, protection, reservation, or verified release.
- A qualifying reclaim predicate moves `normal` to `reclaim` immediately, while hard reclamation waits for a continuously qualifying reclaim-or-worse elapsed-time interval to satisfy its dwell. The dwell persists through `reclaim -> critical -> reclaim`; entry to `recovery_pending` or invalid evidence resets it. The critical predicate moves any controller to `critical` immediately. Clearing critical moves an active controller to `recovery_pending` when the recovery predicate qualifies and to `reclaim` otherwise. Only an already-active controller may enter `recovery_pending`; sustained elapsed-time recovery qualification exits to `normal`, while renewed pressure returns to the matching active phase. Invalid evidence also resets recovery stabilization but never grants or clears reclamation authority.
- Evidence validity is orthogonal to pressure phase. A fresh invalid observation resets hard-action dwell and recovery qualification but cannot initiate measured pressure, prove recovery, or clear an active episode. It latches any already-active phase and selects the operation's monitoring-degraded fallback or refusal. The live pressure episode contains every active canonical pressure constraint, including residency-domain and host-floor constraints; it adds newly active constraints, removes only constraints whose recovery exit stabilizes, and ends only on a fresh coherent vector with no active pressure phase.
- One server pressure monitor owns event coalescing and polling policy. Providers expose event hints, samples, identities, uncertainty, and health. The monitor canonicalizes each hint to its complete observation-dependency set, transitively coalesces overlaps, permits one refresh flight per dependency component, and assembles facts within the cataloged skew and uncertainty bound. It atomically publishes one synthetic observation generation only after validating identities and source-local event ordering. A latched newer event makes an in-flight sample diagnostic-only until a catch-up refresh covers that event generation. A small server-defined, catalog-selected polling profile acts as both event watchdog and eventless fallback, runs more slowly in `normal` and faster during an episode, and always stays within the freshness bound. Controller qualification uses monotonic elapsed time rather than sample counts. Adapters expose no cadence policy, and public configuration adds no per-adapter polling knobs.
- Every automated constraint exposes a catalog-reviewed, dimensionless, monotone recovery-progress projection with a positive reference span and a conservative action-effect algebra. The algebra is commutative, associative, identity-preserving, and saturates at the recovery target. Values use canonical integer units and exact rational comparisons; an unrepresentable interaction, invalid value, or arithmetic overflow fails the scoring cell closed. Such a signal may still support monitoring and reporting but cannot enter automated optimization.
- Admission is predictive and plans the complete reclamation set before changing residency. Unknown or insufficiently confident incoming demand refuses before reclamation or spawn; never evict residents merely to discover whether a model fits. A discovery spawn requires either one reservable finite union of every candidate's complete lifetime envelope under one recovery authority or an externally enforced complete envelope. A fallback may run only when its own manifest is complete and sufficiently confident; it cannot repeat the same operation with unknown overlap or an incomplete lifetime envelope.
- Pressure reclamation and admission reclamation share eligibility rules. A pinned or in-use model vetoes automatic hard reclamation.
- Soft reclamation may clear reconstructible idle state such as a KV cache while preserving weights, the backend process, and any pin.
- A resident's reclamation recency is `last_became_idle_at`: the monotonic instant when the final resident-use lease releases and active use reaches zero after any owned routed operation, including failure or cancellation. Load commit supplies recency only until the resident is first used. Monitoring, maintenance, and soft-reclamation actions do not reset it.
- One server-owned warm-retention duration classifies an idle resident as warm until its recency age expires and cold afterward. The concrete duration remains cataloged implementation design rather than per-adapter policy.
- First discard every action set that violates evidence, protection, leases, dependency order, reservation, or complete feasibility. Preserve this total stratum order: complete soft-only plans before any hard reclamation; otherwise a cold unpinned idle hard-reclamation skeleton; then a warm unpinned idle tail only when required. A soft action may join a hard plan only when its conservative guaranteed effect reduces or eliminates that hard tail, and every admitted soft action executes before hard actions subject to prerequisites. Within an otherwise fixed skeleton, prefer soft reclamation from unpinned residents before pinned residents. Age alone never triggers hard reclamation without admission demand or measured pressure.
- Score a complete action set against the immutable pressure recovery deficit vector. A total priority band combines the server-owned safety class, controller phase, and severity tier. Host-safety constraints precede capacity constraints by default; only reviewed central catalog policy may define another total safety order. Within each band, maximize, in order, the number of constraints reaching recovery exit, the exact sum of capped recovery fractions, the minimum recovery fraction, and the lexicographically greatest ascending-sorted recovery vector. After every band ties, minimize distinct affected residents, total action count, and then the lexicographically sorted canonical action-ID tuple. Reject inclusion-redundant sets. Count a shared allocation once per allocation group and apply its effect once to each genuinely affected constraint.
- Use the same comparison kernel to select the complete set and its deterministic first action. Within the fixed set and stratum, compare dependency-ready actions against the frozen residual vector, then break ties by oldest `last_became_idle_at`, resident ID, and action ID. Persist the set key and first-action residual and comparison key in the explanation. Reload cost does not affect pressure-recovery utility.
- NPU/FLM conflict planning resolves the effective device and slot policy before eviction. If any conflicting resident is pinned or in use, reject the incoming load without changing residency.
- A pinned newcomer has no precedence over a pinned incumbent. Reconfiguring a live pinned model requires explicit unpin or an explicit force operation.
- Load-failure retry may reclaim only eligible unpinned idle models. It never performs an unconditional evict-all retry.
- Manual unload, explicit force, service termination, dead-backend pruning, same-epoch owner-scoped job cleanup, and prior-epoch `owner_scoped_cleanup` remain distinct explicit or lifecycle operations.
- Runtime pinning follows upstream load and pin semantics. Durable pin persistence is a separate per-model recipe-options operation that patches only `pinned` and preserves every unrelated saved option.
- Every request acquisition and release, runtime pin change, manual lifecycle action, backend-state transition, and automatic planner uses one server-owned per-resident state machine. An `idle` to `soft-reclaiming` action lease requires the resident not be in use but may preserve a pin; an `idle` to `hard-reclaiming` lease requires it be unpinned and not in use. New inference, pin, and lifecycle acquisition must wait or receive an explicit retry or refusal while an action lease owns the resident.
- A plan coordinator owns one constraint ledger. Every plan resolves a complete claim set for memory-domain and host effects, per-type count slots, compatibility slots, adapter-declared constraints, and the full ordered action-lease set. It acquires all claims atomically in deterministic order before the first side effect; all competing plans and acquisitions contend with the ledger, and the reservation remains until claims transfer to a terminal occupancy or release state. Admission, measured pressure, NPU conflict, startup loading, and load-failure retry all use this boundary and abandon stale plans before mutation.
- Reconcile every incoming load before advancing or committing its plan. Verify the resolved backend, device, topology, liveness, actual per-domain and host effects, count and compatibility occupancy, and required signal freshness; then atomically convert the matching reservation into provisional occupancy. Initial realization may narrow a candidate union or lifetime envelope only when reviewed evidence proves an excluded effect impossible for the authority's remaining lifetime or an external growth gate prevents it until a new reservation commits; low current usage never narrows an ungated lifetime maximum. Excess use, ambiguity, or identity/topology deviation aborts the plan. Never enlarge a reservation opportunistically after side effects begin.
- Reserve persistent residency and operation demand separately. Every request reserves its transient effects and the maximum persistent-retention alternatives for KV growth, compiled graphs or kernels, allocator reserves, component caches, and other effects that may survive completion. Terminal reconciliation transfers only prepared, verified retained allocations into persistent occupancy before releasing the verified remainder. Unprepared retention is an envelope violation, not a post-effect enlargement. Lazy or autonomous allocation requires a conservative lifetime maximum or an external growth gate; otherwise the affected operation uses a separately complete cataloged fallback or refuses before the effect.
- Admission and other non-pressure reclamation plans execute their reserved actions sequentially. The first non-success terminates the plan, prevents an incoming load, preserves untouched residents, and retains every verified successful release without automatic reload. Each executed target transfers atomically to verified-intact residency, verified release, or quarantine before the plan advances or closes.
- Each pressure-reclamation plan may execute only its deterministic first action. Reconcile that action and close the plan before any fresh pressure plan; the unused tail proves complete feasibility but never inherits execution authority after the deficit vector changes. Verified recovery persists without automatic reload. If pressure remains, release the untouched tail and let a later eligible coordinator attempt build a new complete plan from fresh evidence. Untouched residents remain unchanged.
- `complete_action_and_close_plan` is one server-owned transaction under the lifecycle mutation gate. It validates the reconciled outcome and required generations; transfers the executed target's action lease and complete claims to exactly one verified-intact resident, verified release, or full plausible-claim quarantine disposition; records causal exclusions, outcome, and retry eligibility; closes the plan and releases only untouched-tail reservations; and publishes the outcome and new ledger generation before overlapping work proceeds. No executed-target claim, lease, exclusion, plan closure, or tail reservation changes visibility before this commit. Commit failure retains maximum plausible claims and a protective fence, blocks the smallest affected lifecycle-mutation scope derived from the ownership, topology, and claim closure, exposes recovery-required state, and permits only catalog-authorized remediation or established cleanup authority.
- A verified-intact action failure records the narrowest cataloged causal exclusion for the pressure episode, keyed by action kind, mechanism contract, target runtime, allocation and claim scope, failure class and cause, and failure-relevant contextual binding. Unrelated generation churn carries the exclusion. Lift or narrow it only after fresh reviewed evidence proves the causal condition changed or recovered; the episode's end clears it. Ambiguous or unreachable outcomes quarantine the complete plausible ownership, topology, and constraint-claim closure.
- Ordinary routing, resident use, admission, growth, and automatic planning must prove their complete claim scope disjoint from quarantine. A scoped recovery-remediation token may intersect only to strengthen quarantine, refresh or rebind evidence, clean proven-owned resources, catch up the ledger, or verify release. It cannot route, admit, grow, weaken claims, bypass verified release, or override pin or in-use protection. Separately authorized unload, unpin, force, service termination, and owner-scoped cleanup retain their lifecycle semantics and cannot bypass an existing reservation.
- Each transitively overlapping claim and eligibility component owns one pressure-coordinator epoch with at most one outstanding scheduling attempt, one outstanding retry token, one fair queue, and one monotonic next-eligible retry. On actionable pressure, a brief gate snapshots candidates and blocks only conflicting new resident-use leases; existing use continues. Planning has a cataloged monotonic deadline and either atomically reserves a complete set or publishes a terminal no-plan reason and releases the gate. A protected in-use candidate enters an observable bounded `waiting_for_in_use` state; timeout never grants reclamation authority.
- Under reclaim pressure, a wait timeout or infeasible plan reports unresolved pressure, releases the fence, and grants a bounded fairness window. Previously queued leases run in stable FIFO order within their priority class before the next ordinary attempt; new arrivals cannot jump. Retry occurs only when a target becomes idle, pressure worsens, a policy-relevant dependency changes, or a centrally cataloged positive, monotonic, capped unchanged-state backoff expires. The closed material-change set covers phase or deficit, evidence health or freshness, claims, protection or use, causal exclusions or action availability, mechanism health, topology, configuration, catalog or profile identity, and other reserved-plan dependencies. Repeated samples do not reset backoff.
- An affected resident-use request may proceed during reclaim only when its complete lifetime manifest is both nonincrementing for every active or latched pressure dependency and noninterfering with every eligible recovery resident and lease. Revalidate at lease acquisition. Critical pressure may preempt the fairness window and refuses every new intersecting ordinary route or resident-use lease, admission, growth transaction, and automatic lifecycle plan; the pressure coordinator's own bounded recovery attempts continue under its epoch rules. Explicit safety-reducing lifecycle actions and catalog-authorized recovery remediation retain their bounded authority. Pins remain a hard veto for automatic hard reclamation; an existing pinned use continues, and queued pinned use may wait behind selected soft reclamation.
- Automated fallback requires complete trustworthy signals, effects, claims, recovery authority, and verified release. A combination lacking that evidence remains report-only for measured pressure and refuses capacity-dependent automatic reclamation rather than guessing.
- If admission cannot create a safe plan, or measured pressure remains after all eligible actions, refuse or stop and report the unresolved condition rather than reclaiming a protected model or making arbitrary extra changes.
- `lemond` owns the operational explanation contract. Under the four core API prefixes above, canonical `GET /residency`, admin `GET /residency/operations/{id}`, capability-scoped `GET /residency/operations/{id}/status`, structured logs, and compatibility projectors consume one generated schema and the same immutable explanation revision. Each record exposes typed configured intent, per-operation capability and concrete effective mode, fallback rule, catalog and evidence identity, footprint confidence, ordered reasons, bounded actions and outcomes, terminal state, and retention metadata. Clients render this server-owned truth and never reconstruct policy.
- Public server configuration stays small and intent-oriented. The canonical durable settings are `memory_pressure_reclamation=automatic|report_only|disabled` (default `disabled`), `load_pinned_models_on_startup=false`, nullable positive `residency_memory_limit_gib`, and the independent existing `max_loaded_models` count ceiling (`1` by default, `-1` for unlimited). That ceiling counts every committed resident, including runtime-pinned residents. A saved pin preference is not residency, while each provisional startup member reserves its complete count claim until grouped commit or rollback. Predictive memory-capacity admission is fixed policy, not a public switch. Hatchery uses `max_loaded_models=-1` with automatic pressure reclamation.
- Under those same four prefixes, `GET|PUT /residency/configuration` is the conditional, journaled authority for restart-relevant residency settings. GET returns persisted and effective values, path and root generations, and one strong configuration ETag. PUT requires that ETag through `If-Match` and applies a typed `{set,reset}` patch while preserving unrelated paths; a stale or namespace-wrong validator returns the generated HTTP 412 precondition failure without publishing. Versioned `GET /params` may project durable-only state, but `POST /params` cannot mutate it; local/admin `POST /internal/set` remains last-writer-wins only by atomically binding the current generation at entry and using the same journaled transaction. Sensor choice, calibration machinery, numeric controller profiles, and victim-planning internals remain derived.
- Recipe options are the canonical saved-pin authority, runtime pin remains resident state, and `load_pinned_models_on_startup` remains separate server policy. Under the four core prefixes, conditional `GET|PUT /models/{id}/pin-preference` and `GET|PUT /models/{id}/runtime-pin` support remote clients; upstream-compatible `POST /load`, local/admin `POST /internal/pin`, and legacy `GET /pins`, `POST /pins`, and `DELETE /pins/{model_name}` remain generated compatibility adapters until their announced boundary.
- Each legacy eviction, memory-limit, GTT, and pin input has its own source-bound migration journal, authority root, generation, exact cutover, and conflict policy. Readers use only a validated published root. An absent root fails closed; a failed publication may continue a prior validated root for reads while fencing dependent writes and automatic work. Every publication raises the minimum compatible residency schema, and downgrade requires an explicit quiesced authority export.
- Lifecycle explanations, coordinator records, artifact-writer results, staged-import sessions, and artifact-quarantine records are distinct bounded resource families. Explanation projections never become lifecycle, claim, model-identity, or artifact authority. Ambiguous artifact or identity effects transfer their complete plausible state and fences into a durable quarantine record whose origin-specific clear table is the only release path.
- One generated registry owns operation phases and outcomes, reason spelling and order, presentation and detail schemas, HTTP mappings, endpoint/auth compatibility, and conformance fixtures. Known reasons are bounded and safe to render; unknown schema-minor reasons never authorize policy. Detail survives for 24 hours, then a tombstone survives until seven days after terminal time; active and recovery-required authority never expires.
- Artifact acquisition, registration-capable pulls, staged import and adoption, model deletion, and shutdown obey the same ordered configuration, migration, identity, artifact-writer, recipe-options, and lifecycle authorities. Strong artifact mutation uses durable writer fences and verified native-family completion. Ambiguity transfers authority, keeps identity and writer fences, and returns the generated non-release result until the origin-specific clear row closes. For verified outcomes, compatibility routes retain upstream status, body, and authentication semantics through the declared major boundary.
- These behavioral guarantees and public vocabulary are fixed for the portable specification. The matrix and Hatchery campaign fix the first evidence and promotion contracts; concrete adapter wire shapes, harness implementation, catalog deployment bindings, and physical qualification remain implementation work.
- The implementation handoff consumes the portable matrix's per-operation and affected-domain-set cells, primary evidence, backend recovery authority, concrete fallback or refusal, and conjunctive promotion suites. Validation includes concurrent-daemon owner exclusion; crash injection before spawn, immediately after process creation but before launcher return or record update, during provisional loading and commit, during rollback, and after committed residency; plus complete descendant cleanup, PID reuse, truncated or malformed records, claim replay, and readiness gating for every supported subprocess-ownership model.

## Frontend Split

- `src/app/src/renderer/` is the shared React renderer.
- The Tauri desktop app uses `src/app/src-tauri/` and installs `window.api` through `tauriShim.ts`.
- The browser web app in `src/web-app/` reuses the shared renderer with a separate package/dependency tree.
- Do not consolidate `src/app/package.json` and `src/web-app/package.json`; the split supports Debian native packaging with system Node modules.

### Accepted residency UI target

- Runtime pin state, saved pin preference, and startup-loading policy use distinct controls and labels. A pin action never silently changes the startup policy.
- Saved pin preferences and startup failures remain visible when their models are not loaded so users can retry, change options, or remove the preference.
- The startup-loading setting is server-owned lifecycle configuration. It must not move into per-client desktop or web-app settings.
- Residency rows and persistent recovery messages surface loaded, in-use, pinned, remembered-pin, startup-provisional, committing, rolling-back, suspended, cleanup-required/quarantined, soft-reclaimed, pressure-reclaimed, and refusal states with text or accessible names in addition to color. Provisional members are never presented as loaded or pinned.
- Resource telemetry distinguishes GTT/shared GPU memory from host memory on platforms where that distinction is meaningful.
- Follow `DESIGN.md` and `.impeccable/design.json` for the Impeccable v4 product language. Current CSS that contradicts those documents is implementation debt, not a design-system exception.

## Before Changing Architecture

1. Read the relevant user-facing docs first to infer intended behavior.
2. Read the source paths above.
3. Check whether the behavior is an upstream invariant, a fork-local policy, or an implementation accident.
4. If the change deliberately alters architecture, record the decision in `docs/adr/` when it is hard to reverse, surprising, and trade-off driven.
